# chimera

Пассивный сенсор сети и хоста из частей на разных языках, которые сводятся в одну базу: ядро захвата на C, агенты на Bash и PowerShell, анализ на Go, хранилище на SQL. Идея в том, чтобы сопоставлять то, что видно в сети, с тем, что происходит на хосте.

Мониторьте только сети и хосты, которыми вы владеете или на наблюдение за которыми у вас есть разрешение.

## Статус

Сделано: ядро на C (чтение pcap, разбор Ethernet/IP/TCP/UDP, DNS, SNI из TLS ClientHello, запись в SQLite) и анализатор на Go (находит подозрительный DNS, маяки, расхождения имени и адреса, сканирование, привязку к процессам, HTTP API). Остальное в планах, см. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Быстрый старт

```bash
make -C core            # собирает core/build/chimera-core (нужны компилятор C и libsqlite3)
core/build/chimera-core read capture.pcap --db events.db
sqlite3 events.db "SELECT qname, count(*) FROM dns_events GROUP BY qname ORDER BY 2 DESC LIMIT 10"
sqlite3 events.db "SELECT sni, count(*) FROM tls_events GROUP BY sni ORDER BY 2 DESC LIMIT 10"
make -C core test       # тесты под ASan и UBSan

go build -o build/chimera-analyze ./analyzer/cmd/chimera-analyze
build/chimera-analyze report --db events.db            # находки текстом (--json, --min medium)
build/chimera-analyze serve  --db events.db            # http://127.0.0.1:8088, только чтение
sh scripts/e2e.sh       # весь путь: синтетический pcap -> ядро -> SQLite -> анализатор
```

Демо-захват (`python3 scripts/make_demo_pcap.py demo.pcap`) целиком придуман: адреса из документационных диапазонов, один клиент «маячит» на сервер раз в минуту и спрашивает сгенерированное имя.

## Что умеет ядро

- Читает классический pcap (оба порядка байт, микро- и наносекундные метки). Канальные уровни: Ethernet (с VLAN 802.1Q/ad), Linux cooked, BSD loopback, raw IP.
- IPv4 и IPv6 (с расширенными заголовками), TCP и UDP. Нефрагментированные и первые фрагменты.
- DNS: имя запроса, тип, код ответа, до восьми ответов (A, AAAA, CNAME) со сжатием имён и защитой от циклов указателей.
- TLS: `legacy_version` и SNI из ClientHello, если он целиком в первом сегменте.
- SQLite: потоки (пятёрка, число пакетов и байт, первое и последнее время), события DNS и TLS, индексы под типичные запросы. Схема в [sql/schema.sql](sql/schema.sql).

## Что находит анализатор

| находка | что значит |
| :-- | :-- |
| `dns-high-entropy`, `dns-long-name`, `dns-many-subdomains`, `dns-nxdomain-rate` | имена, похожие на сгенерированные, или данные, зашитые в имена; много NXDOMAIN |
| `beacon` | один клиент открывает TLS к одному адресу через равные промежутки (6 и более раз, разброс до 15%) |
| `sni-ip-mismatch`, `sni-ip-never-resolved`, `tls-no-sni-unresolved` | имя в TLS не сходится с тем, что вернул DNS, или адрес вообще не резолвился в захвате |
| `fan-out`, `port-spread` | один источник обращается к очень многим адресам или портам |
| `unattributed-connection` | соединение с хоста, у которого есть агент, но агент его не видел (нужна таблица `host_connections`) |

Это эвристики: находка означает «посмотрите», а не вердикт. Обновления, keepalive и CDN выглядят так же, поэтому уровни не выше medium. Определение «домена» берёт последние два label без списка публичных суффиксов, `co.uk` посчитается как `co.uk`.

Страница `serve` слушает только 127.0.0.1, не изменяет базу и экранирует все данные; на другой адрес нужен явный `--allow-remote`, аутентификации в ней нет.

## Как проверялось

- Тесты собирают пакеты побайтно (в тесте, не из библиотеки разбора), так что разборщики проверяются по формату на проводе, а не сами по себе.
- Сотни обрезанных и испорченных pcap-файлов прогоняются под AddressSanitizer и UndefinedBehaviorSanitizer; данные до места повреждения сохраняются.
- Анализатор: тесты каждого детектора на вручную собранных событиях (в том числе «нет ложных срабатываний» на обычном трафике), тесты на базе, созданной по настоящей `sql/schema.sql`, HTTP-страница проверена на экранирование враждебных имён.
- Сквозной тест `scripts/e2e.sh`: синтетический pcap, ядро, SQLite, анализатор; падает, если маяк или сгенерированное имя не найдены.
- CI собирает и запускает всё на Linux.

## Фаззинг

В `core/fuzz/` лежат четыре харнеса в стиле libFuzzer (`fuzz_dns`, `fuzz_tls`, `fuzz_decode`, `fuzz_pcap`) и сиды из синтетического pcap. Их гоняет мой фаззер [wyrm](https://github.com/rephuren/wyrm) под ASan и UBSan:

```bash
WYRM=../wyrm sh core/fuzz/build.sh      # нужен clang и собранный wyrm (make в его каталоге)
../wyrm/build/wyrm fuzz --target core/fuzz/build/fuzz_decode --corpus /tmp/c --seed-dir core/fuzz/seeds/decode --persistent --jobs 4 --max-seconds 60
```

Результат разового прогона (ноутбук, 4 воркера, по 60 секунд на DNS, TLS и decode, 120 секунд на pcap с загрузкой в SQLite): около 5,6 млн запусков на каждый из первых трёх и 0,9 млн на `fuzz_pcap`, **падений 0**. Это значит только то, что за это время и на этих сидах wyrm ничего не нашёл; доказательством отсутствия багов это не является, а покрытие у `fuzz_dns` и `fuzz_tls` небольшое (76 и 43 ребра): это маленькие парсеры. Чтобы убедиться, что харнес вообще способен находить ошибки, в копию `dns.c` намеренно внесён выход за границу буфера (размер буфера 256 заменён на 1024 в вызове `read_name`): wyrm нашёл переполнение стека за менее чем минуту.
Ограничения: wyrm (учебный фаззер) слабее AFL++ и libFuzzer, прогон был коротким и не повторялся с разными сидами генератора, прогона на Linux нет, в CI фаззинг не входит.

## Ограничения

- Только классический pcap. pcapng не поддерживается и откажет с понятным сообщением.
- Нет сборки TCP-потока: ClientHello, не поместившийся в первый сегмент, разобран может быть не полностью.
- Нет QUIC и TLS 1.3 ECH (там SNI зашифрован), нет DNS поверх TCP и HTTPS.
- Живой захват через libpcap пока не сделан, ядро читает готовые файлы. Тесты шли на синтетических пакетах и не на реальном трафике.
- Ядро не проверялось на файлах из большого реального захвата; только на собранных вручную. Пороги анализатора (энтропия 3,6, маяк при разбросе до 15%) выбраны по здравому смыслу и синтетике, а не подобраны на реальном трафике: ложные срабатывания на нём возможны и пропуски тоже.
- Есть агент для Linux на Bash (`agents/linux/chimera-agent.sh`, снимок `ss -tnp`, пишет в `host_connections`). Проверен на сохранённом выводе `ss` и в e2e, на живом Linux-хосте в разработке не запускался. Нужен root, чтобы видеть процессы других пользователей; только TCP, соединения короче интервала снимков он не увидит. Агент для PowerShell не написан.
